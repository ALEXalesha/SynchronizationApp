# SyncGlass на C# — проект

26.09.2026. Решения Алексея: две версии параллельно (как Paint); общие файлы
в `%APPDATA%\SyncGlass`; код в том же репозитории в `csharp/`; перенос «законы
сначала, модуль в модуль»; один номер версии на обе.

## Цель

C#/WPF-версия SyncGlass, которая ведёт себя так же, как Electron-версия 1.1.1:
те же деревья, тот же предпросмотр, та же отмена по «Стоп», те же тексты в окне,
те же файлы на диске. Выигрыш — в 4–5 раз меньше места и заметно меньше памяти.
Electron-версия остаётся и получает все будущие правки наравне с C#.

Не цель: новые возможности, другой вид, другая архитектура. Всё, что C#-версия
делает иначе, чем Electron, — ошибка переноса, если здесь не сказано обратного.

## Часть 1. Из чего состоит

```
SynchronizationApp/
├─ main.js, src/, renderer/, test/   Electron (правка одна - общая блокировка)
├─ fixtures/                         образцы общих файлов, их читают тесты обеих версий
└─ csharp/
   ├─ SyncGlass.sln
   ├─ src/SyncGlass.Core/            net8.0, без WPF
   │   ├─ Paths.cs     ← src/paths.js
   │   ├─ Sync.cs      ← src/sync.js
   │   ├─ Plan.cs      ← src/plan.js
   │   ├─ FsOps.cs     ← src/fsops.js
   │   └─ Backend/     ← main.js: Settings, History, SizeCache, ScanCache, Crawl,
   │                     InstanceLock, Backend.cs (13 методов = 13 обработчиков IPC)
   ├─ src/SyncGlass.Wpf/             net8.0-windows, CommunityToolkit.Mvvm
   │   ├─ MainWindow, PreviewWindow, HistoryWindow   ← renderer/index.html
   │   ├─ ViewModels/                                ← renderer/renderer.js
   │   ├─ Glass.xaml                                 ← renderer/styles.css
   │   └─ Services/WindowPlacement.cs                ← копия модуля из Paint
   └─ tests/SyncGlass.Tests/         xUnit
```

Правило имён: класс или файл C# называется как модуль JS, метод — как функция JS
в PascalCase (`pairUp` → `PairUp`, `restoreStage` → `RestoreStage`). Комментарии
«почему» переносятся вместе с кодом, на русском. Так правка, найденная в одной
версии, находит своё место в другой без поиска.

Окно зовёт ядро не через IPC, а через интерфейс `IBackend` с теми же 13 методами:
`GetSettings`, `SaveSettings`, `GetHistory`, `ClearHistory`, `PickFolder`, `Probe`,
`ListFolders`, `Preview`, `CancelPreview`, `Sync`, `CancelSync`, `StartCrawl`,
`StopCrawl`. Интерфейс нужен тестам окна: они подставляют поддельный Backend так же,
как `renderer.test.js` подставляет `window.api`.

Допустимые отличия от «один к одному» (в Node такого нет):
- промисы и `runPool` → `Task`, `SemaphoreSlim`/`Channel`; `walkTree` остаётся
  пулом работников над стеком с тем же числом работников;
- события прогресса → `IProgress<T>`; токены `crawlToken`/`previewToken`
  и флаг `syncStopped` → `CancellationToken`;
- в окно из фона — только через `Dispatcher`, прогресс не чаще тех же 100–150 мс.

## Часть 2. Как идут данные

Цепочки повторяют `main.js` строка в строку по смыслу:

- **Предпросмотр:** `AssertRootsReachable` → `RestoreBothStages` →
  `BuildRunPlan` (сканер: индекс обхода, если он полный и моложе 15 минут, иначе
  живой скан с кешем 15 минут) → `CountByFolder` + `Summarize`. Никогда не бросает:
  отвечает `Aborted` или `Error` с тем же русским текстом.
- **Запуск:** замок «уже идёт» → проверка корней до любого движения файлов →
  `RestoreBothStages` → план → `ApplyPlan` с журналом и `.sgundo` → сброс кешей →
  запись в историю (только если было что делать).
- **Стоп:** `CancelSync` ставит флаг, `ApplyPlan` проверяет его между файлами
  и откатывает журнал в обратном порядке фаз.
- **Фоновый обход:** сначала кеш размеров с диска кусками по 5000, затем обход обеих
  сторон с проверкой корня до и после, предел 300 000 записей (режим «До 300k»),
  периодическое сохранение кеша 5–40 с, только если обход ещё текущий.

### Общие файлы — договор двух версий

Обе версии читают и пишут одни и те же файлы в `%APPDATA%\SyncGlass` в одном
формате. Запись всегда атомарная: временный `*.N.tmp`, затем переименование.

| Файл | Формат (как пишет Electron 1.1.1) |
|---|---|
| `settings.json` | `{localPath, networkPath, direction: "toNetwork"/"toLocal", sort: "name"/"date", sizeMode: "off"/"capped"/"full"}` |
| `history.json` | массив, новые сверху, ≤200 запусков, поимённый список у 20 последних, ≤5000 файлов в записи; `time` — ISO UTC с миллисекундами и `Z` |
| `sizecache-<md5>.json` | `{localPath, networkPath, entries:[{relPath, sizeLocal, cntLocal, sizeNetwork, cntNetwork}]}`; имя — md5 от `localPath + "\0" + networkPath` в UTF-8; храним 6 последних |
| `window-state.json` | `{x, y, width, height, maximized}`, окно всегда 900×600 |
| `.sgundo\` в корнях | служебная папка отката; раскладка — зеркало путей приёмника, как у `restoreStage` |

Значения `sort` и `sizeMode` проверены по `index.html` (`name`/`date`,
`off`/`capped`/`full`). Отметки галочек в файлы не пишутся ни одной версией.
Образцы всех файлов лежат в `fixtures/`. Тесты договора: C# читает образцы, записанные
JS, и пишет свои, которые читает JS-тест; одна и та же пара путей даёт одно имя
файла кеша в обеих версиях; брошенная одной версией `.sgundo` разбирается другой.

### Общая блокировка

Сейчас второе окно Electron не даёт открыть `requestSingleInstanceLock`, а C#-версия
её не видит. Обе версии на старте занимают именованный канал
`\\.\pipe\SyncGlass-<имя пользователя>`: кто занял первым — работает, второй
отправляет в канал «покажись», первое окно выходит вперёд, второй процесс
закрывается. Канал освобождается сам, когда процесс умирает, поэтому «зависшей»
блокировки после вылета не бывает.

Риск: поведение первого экземпляра канала у Node (libuv) и .NET
(`NamedPipeServerStream` с одним экземпляром) должно отказывать друг другу.
Это первое, что проверяется пробой, до любого другого кода. Если не сработает —
запасной вариант: файл `instance.lock` с PID и временем старта процесса.

## Часть 3. Окно

Повторяет Electron-окно: 900×600, без изменения размера, тёмные полупрозрачные
панели со скруглением (без размытия фона — его нет и в Electron). Шапка
(направление, «История», «Обновить»), строка состояния (точка-индикатор, число
объектов, «Размеры» Выкл/До 300k/Без лимита, «Сортировка»), два дерева, низ
с папками и «Синхронизировать». Тексты — дословно из `index.html`/`renderer.js`.

- Деревья ленивые, по уровню (`ListFolders` на раскрытие), с виртуализацией
  (`VirtualizingStackPanel`, как лента истории в Paint 1.34): на 300 тысячах
  записей разворачивается только видимое.
- Галочки: состояния «да / нет / частично», наследование от родителя, отметки
  по `markKey` без учёта регистра — логика `renderer.js` переносится во ViewModel
  как есть.
- Проба доступности каждые 6 с и лёгкое перечитывание верхнего уровня, как
  `probeTick`/`lightRelistTop`.
- Предпросмотр — модальное окно: счётчики по действиям, по веткам, закрытые
  правами папки, предупреждение «удаление безвозвратно», живой счётчик,
  «Стоп». История — отдельное окно с тем же пределом деталей.
- Место окна — модуль `WindowPlacement` из Paint, файл общий с Electron.

## Часть 4. Тесты, сборка, выпуск

**Тесты пишутся раньше кода** и переносят `test/*.test.js` файл в файл:
`PathsTests`, `SyncTests`, `PlanTests`, `FsOpsTests`, `DeniedTests` (icacls),
`RacingTests`, `StressTests`, `MemoryTests`, `HistoryTests`, `WindowStateTests`,
`BackendTests` (← main.test), `ViewModelTests` (← renderer.test),
`InvariantsTests` (13 законов на случайных деревьях, тот же генератор и та же
проверка его плотности), `ScalingTests` (оси масштаба; обращения к диску
считаются подменённой файловой системой, а не секундомером). Новое:
`ContractTests` по `fixtures/`, `InstanceLockTests`. Закон памяти в C#
считает не промисы, а число одновременно живых задач обхода.

Каждый перенесённый закон проверяется мутацией, как в JS: вернуть ошибку в код,
увидеть красный тест.

Сборка как у Paint: `dotnet publish` одним файлом self-contained и установщик
Inno Setup. Снимки окна — программой (`tools/SyncGlass.Screenshots`), с временной
папкой данных, как `tools/make-screenshots.js`.

CI: в `.github/workflows/ci.yml` и `.gitea/workflows/ci.yml` добавляется шаг
`dotnet test csharp` (на Gitea — без setup-dotnet, .NET уже стоит на ПК).

Выпуск 1.2.0 — общий: C#-версия 1.2.0 и Electron 1.2.0 (общая блокировка
и тесты договора). Один тег `v1.2.0`, в выпуске на GitHub четыре файла:
установщик и portable каждой версии. Описание EN и RU, README EN и RU с разделом
о двух версиях, CHANGELOG. Публикация — через `tools/publish_github.sh` после Gitea.

## Порядок работ

1. Проба общей блокировки Node ↔ .NET.
2. `Paths`, `Sync`, `Plan` + их тесты.
3. `FsOps` (скан, `WalkTree`, `ApplyPlan`, `RestoreStage`) + тесты диска, прав,
   гонок, нагрузки, памяти.
4. `Backend` (настройки, история, кеши, обход, предпросмотр, запуск, блокировка)
   + `BackendTests`, `ContractTests`, `InvariantsTests`, `ScalingTests`.
5. Окно + `ViewModelTests`; сверка снимков C# и Electron рядом.
6. Electron 1.2.0: общая блокировка и тест договора.
7. Сборки, снимки, документация, CI, выпуск 1.2.0.

Оценка: 4–6 длинных сессий. Шаги 2–4 — половина работы.
