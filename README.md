# SyncGlass

Настольное приложение (Windows, Electron) для синхронизации папок между
ноутбуком и сетевым компьютером. Дизайн — liquid glass в стиле Apple.

Слева — дерево локальных папок, справа — сетевых. Отмечаете галочками, что
синхронизировать, выбираете направление и жмёте «Синхронизировать». Приёмник
становится точной копией источника.

---

## Что делает

- Слева дерево локальной директории, справа — сетевой. Видны и папки, и файлы;
  любую папку можно **развернуть** на любом уровне.
- **Чекбоксы у всего** (папки и файлы) стоят на стороне-**источнике** и переезжают
  при смене направления. Отметил папку — синхронизируется вся её ветка; внутри
  можно **снять галочку** с подпапки/файла — они будут исключены (частичная галка
  у родителя). Есть «Выбрать все».
- Переключатель задаёт направление: **Локально → Сеть** или **Сеть → Локально**.
- Приёмник приводится к точной копии источника: новые файлы копируются,
  изменённые перезаписываются, лишние отправляются **в Корзину**.
- **Перемещения распознаются.** Если файл или целую папку переложили в другое
  место, приёмник делает то же самое переименованием, а не «удалить и скачать
  заново». Пара ищется по размеру и имени файла среди исчезнувшего и появившегося,
  и засчитывается только при однозначном совпадении — иначе файл едет обычным
  копированием. Работает и когда файл переехал между двумя выбранными ветками.
  Если файл при переносе ещё и переименовали, пара не ищется: без имени в ключе
  остаются только размер и дата, а этого мало, чтобы не перепутать содержимое.
- **Структура папок синхронизируется.** Пустые папки источника создаются, лишние
  папки приёмника убираются. Папку с чем-то внутри (например, исключённым из
  синхронизации) удаление не тронет.
- **Конфликты «папка против файла» разбираются.** Если на источнике `Отчёты` —
  папка, а на приёмнике файл с тем же именем (или наоборот), приёмник сначала
  расчищает это место, а потом кладёт туда правильное. Раньше такой узел ронял
  предпросмотр или давал горсть ошибок.
- **Регистр имён не различается**, как и в самой Windows: `Docs` и `docs` — одна
  и та же папка. Если стороны пишут имя по-разному, приёмник переписывается под
  написание источника.
- Перед выполнением — окно предпросмотра со сводкой (сколько переместить /
  скопировать / перезаписать / удалить), с живым счётчиком по ходу работы.
  Ничего не меняется без подтверждения.
- **Кнопка «Остановить»** во время работы прекращает синхронизацию и возвращает
  приёмник в исходное состояние: скопированное убирается, перезаписанное и
  удалённое возвращается на место. Возможно это потому, что оригиналы не
  уничтожаются сразу, а на время работы переезжают в служебную папку `.sgundo`
  внутри приёмника и выбрасываются одной пачкой только в самом конце. Если запуск
  оборвался аварийно, следующий разберёт эту папку сам.
- **Сортировка** дерева по имени или по дате изменения.
- **Размеры и число файлов** считаются в фоне при запуске, показываются в строках
  и кешируются на диск; вверху статус-бар с бегущей полоской активности.
  Переключатель «Размеры»: **Выкл** (дерево работает мгновенно, для сотен тысяч
  файлов), **До 300k** (безопасный предел — обход сам остановится, чтобы не съесть
  память) или **Все** (без ограничения — для мощных машин, нужно больше памяти).
- **Индикаторы доступности** (зелёная/красная точка в заголовках панелей):
  доступность папок проверяется каждые несколько секунд, «нет в сети» само
  исправляется, когда сеть возвращается.
- **Недоступная сторона блокирует запуск.** Отсутствующая папка читается пустым
  списком, а пустой источник по логике зеркала означает «на приёмнике всё лишнее»,
  поэтому синхронизация в таком случае просто не начинается.
- **Приложение открывается в одном экземпляре** — вместо второго окна поднимается
  уже запущенное: две копии делили бы служебную папку на приёмнике.
- **История синхронизаций** — кнопка «🕘 История» открывает журнал прошлых
  запусков; запись раскрывается в список файлов (что скопировано/перезаписано/
  удалено), удаления подсвечены.
- **Пути, направление и сортировка запоминаются** между запусками.

## Запуск

```powershell
npm install      # один раз
npm start        # запустить приложение
npm test         # прогнать тесты
```

## Сборка (Windows)

```powershell
npm run dist            # портабл + установщик
npm run dist:portable   # только портабл (один exe, без установки)
npm run dist:setup      # только установщик (NSIS)
```

Готовые файлы кладутся в `dist/`:

- `SyncGlass-<версия>-portable.exe` — запускается без установки;
- `SyncGlass Setup <версия>.exe` — установщик с выбором папки и ярлыками.

Сборка не подписана, поэтому SmartScreen при первом запуске может предупредить
(«Подробнее» → «Выполнить в любом случае»).

Если `dist/` занят (открыт проводником или запущена прошлая сборка), electron-builder
падает на очистке каталога. Тогда собирайте в запасной, он в `.gitignore`:

```powershell
npx electron-builder --win nsis portable -c.directories.output=dist-build
```

## Пути к папкам

- **Локальная папка** — обычный путь, например `C:\Users\Имя\Documents`.
- **Сетевая папка** — UNC-путь `\\ИмяКомпа\ОбщаяПапка` или подключённый
  сетевой диск `Z:\`. Папка должна быть расшарена в Windows.
- Папки не должны быть **вложены друг в друга**: `C:\Data` и `C:\Data\backup` —
  это копирование папки внутрь самой себя, синхронизация с такой парой не
  начинается.

## Как работает логика синхронизации

Синхронизация — **зеркальная**: приёмник приводится к точной копии источника.
Какая сторона источник, а какая приёмник — задаёт переключатель направления.

### 1. Сравнение файлов

Для каждой выбранной ветки приложение рекурсивно собирает список файлов на обеих
сторонах и сопоставляет их **по относительному пути** внутри ветки. Для каждого
файла решение принимается так:

| Ситуация | Действие |
|---|---|
| Файл есть в источнике, нет в приёмнике | **копировать** |
| Файл есть в обоих, но отличается | **перезаписать** |
| Файл есть в приёмнике, нет в источнике | **в Корзину** |
| Файл одинаковый | ничего |

«Отличается» = разный размер **или** разное время изменения (mtime). Время
сравнивается с допуском **2 секунды**: разные файловые системы (NTFS, сеть)
округляют mtime по-разному, и без допуска одинаковые файлы считались бы разными.
Содержимое побайтово не сверяется — только размер и дата (это быстро и в 99%
случаев достаточно).

**Регистр в путях не значим.** NTFS и сетевые шары не различают `Docs` и `docs`,
поэтому стороны сопоставляются так же. Иначе один и тот же файл выглядел бы
двумя разными: копия легла бы поверх собственного файла приёмника, а исходное
написание уехало бы в Корзину. Если написание разошлось, файл всё равно
перезаписывается — так на приёмнике остаётся имя ровно в том виде, в каком его
пишет источник.

Правило сквозное — на регистр не смотрит ни одно сравнение путей между сторонами,
и это важнее, чем кажется:

- **Структура папок.** `Док` на приёмнике рядом с `док` на источнике больше не
  считается лишней папкой: иначе `rmdir` сносил бы её сразу после `mkdir`.
- **Конфликты «папка против файла»** ищутся по тому же ключу.
- **Индекс фонового обхода.** Имя ветки интерфейс берёт со стороны, попавшей
  в список первой. Если вторая пишет его иначе, точное сравнение не находило
  в индексе ни одного пути и читало сторону пустой — а пустой источник по логике
  зеркала означает «стереть ветку на приёмнике целиком». Самый опасный случай:
  ловился он только при включённом подсчёте размеров, потому что живой скан
  того же выбора отрабатывал верно.
- **Дерево в интерфейсе.** `Docs` и `docs` — одна строка, а не две, каждая
  с пометкой «нет на другой стороне».
- **Отметки выбора.** Когда сторона возвращается после обрыва, написание имени
  может смениться на её собственное. Ключ отметки подгоняется под новый список,
  иначе выбор разом и стирался, и переставал совпадать со строкой в дереве.

### 2. Конфликты «папка против файла»

Под одним именем на разных сторонах может лежать разное: на источнике `Отчёты` —
папка, а на приёмнике файл, или наоборот. Просто скопировать поверх тут нельзя:
`readdir` по файлу обрывает скан с `ENOTDIR`, `mkdir` упирается в файл, а
копирование файла поверх папки падает с `EPERM`.

Поэтому такой узел разбирается отдельной фазой, самой первой: приёмник целиком
расчищает это место, и только потом идут обычные копирование и создание папок.
Всё, что лежало внутри убранного узла, из плана вычёркивается: к моменту
пофайловой обработки его там уже нет. В сводке предпросмотра конфликты
считаются удалениями, и это честно — с приёмника узел действительно убирается.

Ловятся конфликты и на самой ветке, и в любой её глубине. Убранный узел уезжает
тем же путём, что остальные оригиналы, в служебную папку, поэтому «Остановить»
возвращает его на место. Возвращается он последним из всего: на его месте успела
встать папка из более поздних фаз, и место освобождается только в самом конце
отката.

### 3. Удаление — в Корзину (кроме сетевых папок)

Лишние файлы на приёмнике не стираются навсегда, а отправляются в **Корзину
Windows** (`shell.trashItem`) — их можно восстановить.

Исключение: на **сетевых (UNC) папках** вида `\\Комп\Папка` Корзины не существует,
поэтому там лишние файлы удаляются **безвозвратно**. Предпросмотр в этом случае
показывает предупреждение, а подпись меняется с «в Корзину» на «удалить».

Сколько файлов ушло мимо Корзины, считается поимённо, а не «был ли такой случай».
Служебная папка уезжает одним действием на всё содержимое, поэтому вызов удаления
знает свой вес: иначе один-единственный файл, который Корзина не приняла, красил
бы весь запуск, и отчёт объявлял бы безвозвратно удалённым всё подряд.

### 4. Выбор веток и исключения

- Отметили папку → синхронизируется вся её ветка (рекурсивно).
- Внутри отмеченной ветки можно снять галочку с подпапки → она **исключается**:
  не копируется из источника и не удаляется на приёмнике, остаётся как есть.
  У родителя с исключённой подпапкой галочка становится «частичной» (чёрточка).
- Выбор описывается набором **включений** (корни веток) и **исключений** (дырки
  внутри них). При сканировании исключённые ветки просто пропускаются на обеих
  сторонах, поэтому исключённые файлы гарантированно не трогаются.
- **Самая точная отметка главнее.** Внутри исключённой подпапки можно вернуть
  галочку её вложенной части: отмечено `docs`, снято `docs/a`, снова отмечено
  `docs/a/b` — синхронизируется `docs` без `docs/a`, но вместе с `docs/a/b`.
  Запрет действует только до ближайшей отметки внутри себя.
- Отметки живут в интерфейсе и не пропадают, если сторона на секунду отвалилась:
  недоступная папка читается пустым списком, и по такому списку выбор не чистится.
- Ключ отметки — путь **без учёта регистра**, как и всюду в главном процессе.
  Имя узла в дереве берётся с той стороны, что попала в список первой, и стоит
  второй написать его иначе, как точный ключ переставал совпадать: галочка
  пропадала сама собой, а вместе с ней и папка из синхронизации. Настоящее
  написание при этом сохраняется — его и получает главный процесс.

### 5. Предпросмотр перед выполнением

Перед изменениями показывается окно: сколько файлов будет скопировано,
перезаписано и отправлено в Корзину — по каждой выбранной ветке. Никакие файлы
не меняются, пока не нажата кнопка «Выполнить». Само выполнение идёт **пачкой**
(до 16 файлов одновременно) — по сети это заметно быстрее, чем по одному.

Строка по ветке считает и её собственных родителей: для `год/квартал/неделя` план
создаёт ещё `год` и `год/квартал`, а внутрь ветки они не вложены. Раньше в шапке
они были, а в строке нет — и сумма по строкам не сходилась с итогом. Путь при
этом засчитывается самой длинной подходящей ветке, иначе работа вложенной ветки
утекала бы в родителя, а сама она показывала бы «без изменений».

### 6. Ленивое дерево — быстро даже на больших папках

Дерево грузится лениво: при открытии читаются только имена папок верхнего уровня,
при разворачивании — только прямые подпапки этого узла (один `readdir`).

Файлы читаются **параллельно** (до 32 одновременных запросов) — по сети (SMB), где
всё упирается в задержку каждого запроса, это ускоряет обход в разы.

Создание папок при копировании тоже идёт пачкой: результат `mkdir` запоминается
на всю синхронизацию, поэтому пачка файлов в одну папку обходится одним вызовом,
а не вызовом на файл. Запоминается именно обещание, а не отметка о готовности —
отметка ставилась после ожидания, и вся пачка параллельных копий успевала
проскочить проверку до того, как первый допишет ответ.

Фоновый обход при запуске проходит по всем файлам, считает размеры и **запоминает
по каждому файлу размер и дату**. Когда обход завершён (в статус-баре «Готово»),
предпросмотр и синхронизация **переиспользуют эти данные** и не читают сеть заново —
план строится мгновенно. Если обход ещё идёт, выбранные ветки сканируются вживую.
Данные сбрасываются после синхронизации, при «Обновить» и при смене доступности
стороны. Сверх того у кеша сканов есть свой срок — те же **15 минут**, что и у
индекса: связка «предпросмотр → выполнить» укладывается в минуты, а всё, что живёт
дольше, описывает уже не тот диск. Просроченные записи из кеша сканов
выбрасываются: ключ — это путь ветки плюс исключения, разных за сессию набирается
сколько угодно, а запись держит по строке на каждый файл ветки.

Погашённый обход не дописывает свой черновик на диск: токен гасит не только сам
подсчёт, но и сохранение. Иначе оборванный обход сохранялся уже после того, как
пришедший ему на смену успевал записать полный, и следующий запуск показывал
половину дерева как готовые размеры.

Размеры индексируются по пути **без учёта регистра**. Стороны могут писать одну
и ту же папку по-разному, а строка в дереве одна: при точном ключе размеры
расходились по двум записям, и та сторона, чьё написание в дерево не попало,
не показывалась вовсе — рядом с именем висела пустота.

Готовому обходу верят не всегда. Индекс годится вместо живого скана, только если
каждая сторона была на месте и до, и после обхода: пропавшая посреди работы сеть
даёт частичную картину, а по ней приёмник выглядит лишним целиком. И оба пути,
живой скан и индекс, обязаны давать один и тот же план — это проверяют тесты,
которые строят план обоими способами и сверяют результат.

Пока открыт предпросмотр, фоновая проверка связи не перезапускает обход: сеть
одна, и подсчёт размеров вставал бы вторым потоком поперёк копирования.

В список рисуется не больше **500 строк на уровень** (и на верхнем тоже), остальное
сворачивается в «…ещё N». Дело не в чтении, а в отрисовке: во время обхода дерево
перерисовывается раз в 400 мс, и на папке с десятками тысяч подпапок окно вставало
намертво. На выбор предел не влияет: отметки живут отдельно от строк, поэтому
«Выбрать все» захватывает и то, что не показано.

### 7. Устойчивость к ошибкам

Ошибка отдельного файла не обрывает всю синхронизацию — проблемные файлы
копятся и показываются в итоге, а остальные обрабатываются нормально:

- **Перенос даты** (`utimes`) на сетевых шарах часто запрещён — это не критично,
  файл всё равно копируется (при следующей синхронизации может считаться
  изменённым по дате).
- **Read-only** файлы при копировании/удалении: снимается атрибут и повтор.
- **Исчезнувший источник** (файл удалили уже после сканирования) идёт в список
  ошибок, а не пропускается молча. Если оригинал на приёмнике к этому моменту уже
  отложен в служебную папку, он возвращается на место: заменять его нечем, и без
  возврата файл пропал бы сразу с обеих сторон.
- **Обрыв посреди работы** не оставляет в неведении: окно отдельно сообщает,
  сорвался ли запуск, не успев ничего тронуть, или ошибка случилась уже по ходу
  записи и часть работы сделана.
- Предпросмотр можно **отменить**, при обрыве связи он показывает ошибку, а не виснет.

Отдельно — **защита от «пустого источника»**. Отсутствующую папку сканеры отдают
пустым списком, а пустой источник по логике зеркала означает «на приёмнике всё
лишнее». Поэтому обе стороны проверяются перед тем, как строить план, и синхронизация
просто не начинается, если одна из них недоступна. Ту же осторожность соблюдают
листинг дерева (по нечитаемой стороне список не подменяется) и фоновый обход
(частичный индекс не идёт в план).

**Вложенные корни отклоняются.** Пара вроде `C:\Data` и `C:\Data\backup` — это
копирование папки внутрь самой себя: приёмник растёт по ходу работы, и уже
скопированное на следующем проходе снова выглядит новым. Такая пара не проходит
проверку, и синхронизация не начинается. Регистр и завершающий слэш на проверку
не влияют, а вот соседние `data` и `data2` пересечением не считаются.

**Застрявший оригинал не выбрасывается заодно с мусором.** В конце запуска
служебная папка уезжает в Корзину целиком, одним действием: это на порядок
быстрее, чем по файлу. Но если внутри остался оригинал, который не удалось ни
заменить, ни вернуть на место (путь занят, файл держат открытым), другой копии
у него нет. Тогда папка целиком не трогается: в Корзину уходит поимённо только
то, что записано в журнале, а застрявшее дожидается следующего запуска. Тот
разберёт служебную папку на старте, когда помеха может уже исчезнуть. Осечка на
одном оригинале при этом не отменяет уборку остальных — иначе уже заменённые
файлы вернулись бы на приёмник следующим запуском, как будто их и не удаляли.

**Разбор служебной папки идёт узлами, а не файлами.** Если на месте узла ничего
нет, один `rename` возвращает всё поддерево разом — по сети это одна операция
вместо тысячи. Место занято папкой — содержимое сливается по одному, вглубь.
Пустые папки при этом сохраняются: раньше возврат шёл по списку файлов, а
«пусто ли внутри» считалось тем же списком, и отложенная ветка без единого файла
не возвращалась вовсе — служебная папка проходила по такому счёту как пустая и
стиралась вместе с ней. Теперь содержимое считается обходом каталогов: файл,
ссылка или непустая ветка означают, что узел вернуть не удалось.

Второй экземпляр приложения не запускается: две копии делят служебную папку
`.sgundo` на приёмнике, и разбор брошенных оригиналов одним запуском выдернул бы
их из-под другого. Вместо нового окна поднимается уже открытое.

### 8. История синхронизаций

Каждый непустой запуск записывается в `history.json` (в `userData`): время,
направление, сводка (сколько скопировано / перезаписано / удалено), число
безвозвратных удалений и ошибок, а также список файлов. Хранятся **последние
200 запусков**; в одной записи — до 5000 файлов (удаления в приоритете, остальное
помечается как «…ещё N»). Запись атомарная. Кнопка «История» показывает журнал,
запись раскрывается в список файлов; есть очистка.

Осиротевшие временные файлы (`.tmp`) от прерванных атомарных записей кешей/истории
удаляются автоматически при старте.

## Архитектура

Electron, два процесса, общение через IPC (безопасный мост `contextBridge`):

- **Main (Node.js)** — вся работа с файлами: листинг, параллельное сканирование,
  фоновый обход размеров, сравнение, копирование, удаление, проверка доступности,
  кеши и хранение настроек.
- **Renderer** — интерфейс liquid glass. Файловой системы напрямую не касается,
  только шлёт запросы в main и рисует дерево/статусы/прогресс.

### Модули

- `src/sync.js` — **чистая логика планирования**: на вход два списка файлов, на
  выход план (копировать / перезаписать / в Корзину / без изменений), поиск
  перемещений (`detectMoves`), разница структуры папок (`planDirs`), сводка для
  предпросмотра (`summarize`). Без файловых операций — легко тестируется.
- `src/plan.js` — **сборка плана на весь запуск**: план по одной ветке
  (`planForBranch`, включая конфликты «папка против файла»), слияние всех выбранных
  веток в один план (`buildRunPlan`) — только так виден перенос файла между двумя
  ветками, — чтение ветки из готового индекса обхода (`scanFromIndex`) и счётчики
  по каждой ветке для предпросмотра (`countByFolder`). Файловую систему трогает
  только через `stat` и переданный сканер, поэтому тестируется на временных папках.
- `src/fsops.js` — файловые операции: параллельный рекурсивный скан (с исключениями),
  ленивый листинг детей с датой, фоновый обход дерева (`crawlTree`), выполнение
  плана с устойчивостью к ошибкам отдельных файлов, журнал и откат (`applyPlan`,
  `restoreStage`), служебная папка `.sgundo`.
- `src/paths.js` — проверка вложенности корней друг в друга (`rootsOverlap`) и ключ
  сравнения путей без учёта регистра (`ciKey`), которым пользуются все остальные
  модули. Свёртки вложенных выбранных путей здесь намеренно нет: вложенная ветка
  рядом с родителем — законный выбор (см. «Выбор веток и исключения»), и отбрось
  её как «покрытую», она молча выпала бы из синхронизации.
- `main.js` — Electron main: IPC (листинг, предпросмотр с прогрессом/отменой,
  синхронизация, фоновый обход, проверка доступности `probe`, история), кеш сканов
  в памяти и кеш размеров на диске (`sizecache-*.json`), история (`history.json`),
  настройки (`settings.json`), очистка `.tmp` при старте — всё в `userData`.
- `preload.js` — узкий IPC-мост.
- `renderer/` — интерфейс: `index.html`, `styles.css`, `renderer.js` (дерево,
  трёхпозиционный выбор, сортировка, статус-бар, индикаторы связи).
- `docs/superpowers/specs/` — исходный дизайн-документ (снимок на старте проекта).
- `test/` — юнит- и интеграционные тесты (`node --test`).

## Тесты

```powershell
npm test
```

Пять файлов в `test/`, всё на `node --test`, без внешних зависимостей и без
Электрона: логика вынесена в `src/`, поэтому проверяется напрямую.

- `sync.test.js` — сравнение файлов, поиск перемещений, разница структуры папок,
  сводка, нечувствительность к регистру. Чистые функции, на списках в памяти.
- `paths.test.js` — проверка вложенности корней друг в друга.
- `plan.test.js` — сборка плана на временных папках: слияние веток, перенос между
  двумя выбранными ветками, вложенные ветки и их родители, исключения, конфликты
  «папка против файла», счётчики предпросмотра, ветка в чужом регистре. Отдельно
  сверяется, что план по индексу фонового обхода совпадает с планом по живому
  скану — источники разные, а результат обязан быть один.
- `fsops.test.js` — реальный цикл копирование/перезапись/удаление, изоляция
  вложенной синхронизации, откат по журналу, разбор служебной папки после
  оборванного запуска (включая пустые папки и ветки без единого файла),
  устойчивость `applyPlan` к ошибке отдельного файла и к отказу Корзины,
  а также то, что `mkdir` не уходит на каждый скопированный файл.
- `stress.test.js` — случайные изменения дерева с проверкой, что после
  синхронизации стороны совпадают, а повтор не находит работы; остановка в
  произвольной точке с возвратом приёмника ровно в исходное состояние; ветка на
  200k файлов.

Основной приём проверки — **сравнение деревьев целиком** до и после, а не
отдельных файлов. Так ловятся и лишние следы (пустая папка, оставшаяся от
отката), и молчаливые пропуски, которых по сводке не видно.

## Вне рамок

- Нет облака/сервера/сетевых протоколов — только пути файловой системы.
- Нет автосинка по расписанию — синхронизация по кнопке.
- Сравнение по размеру и дате, без побайтовой сверки/хешей.
