Настольное приложение (Windows, Electron) для синхронизации папок между
ноутбуком и сетевым компьютером. Дизайн — liquid glass в стиле Apple.

Слева — дерево локальных папок, справа — сетевых. Отмечаете галочками, что
синхронизировать, выбираете направление и жмёте «Синхронизировать». Приёмник
становится точной копией источника.

---

## Что делает

- Слева дерево локальной директории, справа — сетевой. Видны и папки, и файлы;
  любую папку можно **развернуть** на любом уровне.
- **Чекбоксы у всего** (папки и файлы) стоят на стороне-**источнике** и переезжают
  при смене направления. Отметил папку — синхронизируется вся её ветка; внутри
  можно **снять галочку** с подпапки/файла — они будут исключены (частичная галка
  у родителя). Есть «Выбрать все».
- Переключатель задаёт направление: **Локально → Сеть** или **Сеть → Локально**.
- Приёмник приводится к точной копии источника: новые файлы копируются,
  изменённые перезаписываются, лишние **удаляются безвозвратно** (Корзина
  не используется — см. раздел 3).
- **Перемещения распознаются.** Если файл или целую папку переложили в другое
  место, приёмник делает то же самое переименованием, а не «удалить и скачать
  заново». Пара ищется по размеру и имени файла среди исчезнувшего и появившегося,
  засчитывается только при однозначном совпадении и **сверяется по содержимому**
  перед тем, как стать перемещением. Работает и когда файл переехал между двумя
  выбранными ветками. Если файл при переносе ещё и переименовали, пара не ищется:
  без имени в ключе остаются только размер и дата, а этого мало, чтобы не
  перепутать содержимое.
- **Структура папок синхронизируется.** Пустые папки источника создаются, лишние
  папки приёмника убираются. Папку с чем-то внутри (например, исключённым из
  синхронизации) удаление не тронет.
- **Конфликты «папка против файла» разбираются.** Если на источнике `Отчёты` —
  папка, а на приёмнике файл с тем же именем (или наоборот), приёмник сначала
  расчищает это место, а потом кладёт туда правильное. Раньше такой узел ронял
  предпросмотр или давал горсть ошибок.
- **Регистр имён не различается**, как и в самой Windows: `Docs` и `docs` — одна
  и та же папка. Если стороны пишут имя по-разному, приёмник переписывается под
  написание источника.
- Перед выполнением — окно предпросмотра со сводкой (сколько переместить /
  скопировать / перезаписать / удалить), с живым счётчиком по ходу работы.
  Ничего не меняется без подтверждения. Большие числа печатаются с разрядами и
  мельче, «из N» во время работы идёт отдельной строкой: шестизначный счёт раньше
  вылезал за рамку плашки (исправлено в 1.0.1).
- **Окно открывается там, где его закрыли** (1.1.0). Сохранённое место проверяется по
  нынешним мониторам: монитор отключили — окно встаёт по центру основного, заголовок
  всегда на экране. Правило — тот же модуль, что в калькуляторах и Paint Pro, со
  свойствами на случайных раскладках экранов.
- **Кнопка «Остановить»** во время работы прекращает синхронизацию и возвращает
  приёмник в исходное состояние: скопированное убирается, перезаписанное и
  удалённое возвращается на место. Возможно это потому, что оригиналы не
  уничтожаются сразу, а на время работы переезжают в служебную папку `.sgundo`
  внутри приёмника и выбрасываются одной пачкой только в самом конце. Если запуск
  оборвался аварийно, следующий разберёт эту папку сам.
- **Сортировка** дерева по имени или по дате изменения.
- **Размеры и число файлов** считаются в фоне при запуске, показываются в строках
  и кешируются на диск; вверху статус-бар с бегущей полоской активности.
  Переключатель «Размеры»: **Выкл** (дерево работает мгновенно, для сотен тысяч
  файлов), **До 300k** (безопасный предел — обход сам остановится, чтобы не съесть
  память) или **Все** (без ограничения — для мощных машин, нужно больше памяти).
- **Индикаторы доступности** (зелёная/красная точка в заголовках панелей):
  доступность папок проверяется каждые несколько секунд, «нет в сети» само
  исправляется, когда сеть возвращается.
- **Недоступная сторона блокирует запуск.** Отсутствующая папка читается пустым
  списком, а пустой источник по логике зеркала означает «на приёмнике всё лишнее»,
  поэтому синхронизация в таком случае просто не начинается.
- **Папки без доступа не мешают работать.** Закрытая правами папка (`System Volume
  Information` в корне диска, чужой каталог на шаре) раньше обрывала предпросмотр
  целиком. Теперь она просто выводится из сравнения — и сразу на обеих сторонах,
  чтобы её содержимое не сочли лишним и не стёрли, — а список таких папок
  показывается в предпросмотре и в итоге. Так же выводится и отдельный файл,
  у которого не читается даже размер.
- **Живая папка не срывает работу.** Файл, который только что был в списке, к моменту
  чтения его размера может уже исчезнуть — так ведут себя временные файлы, кеш
  браузера, каталог сборки. Раньше такая гонка обрывала весь скан: предпросмотр
  отвечал «не удалось прочитать папки», а подсчёт размеров падал на всём дереве
  из-за одного файла. Теперь исчезнувший файл просто не попадает в список.
- **Приложение открывается в одном экземпляре** — вместо второго окна поднимается
  уже запущенное: две копии делили бы служебную папку на приёмнике.
- **История синхронизаций** — кнопка «🕘 История» открывает журнал прошлых
  запусков; запись раскрывается в список файлов (что скопировано/перезаписано/
  удалено), удаления подсвечены.
- **Пути, направление и сортировка запоминаются** между запусками.

## Сборка (Windows)

```powershell
npm run dist            # портабл + установщик
npm run dist:portable   # только портабл (один exe, без установки)
npm run dist:setup      # только установщик (NSIS)
```

Готовые файлы кладутся в `dist/`:

- `SyncGlass-<версия>-portable.exe` — запускается без установки;
- `SyncGlass Setup <версия>.exe` — установщик с выбором папки и ярлыками.

Сборка не подписана, поэтому SmartScreen при первом запуске может предупредить
(«Подробнее» → «Выполнить в любом случае»).

Сборщик - electron-builder 26.15.3 (с 25.09.2026, было 24.13.3). Старый тянул за собой
пакеты с известными уязвимостями (xmldom, tar, js-yaml, undici и другие, `npm audit` - 12,
одна критическая); сейчас `npm audit` - 0. В само приложение эти пакеты не попадают,
только в процесс сборки.

Если `dist/` занят (открыт проводником или запущена прошлая сборка), electron-builder
падает на очистке каталога. Тогда собирайте в запасной, он в `.gitignore`:

```powershell
npx electron-builder --win nsis portable -c.directories.output=dist-build
```

## Пути к папкам

- **Локальная папка** — обычный путь, например `C:\Users\Имя\Documents`.
- **Сетевая папка** — UNC-путь `\\ИмяКомпа\ОбщаяПапка` или подключённый
  сетевой диск `Z:\`. Папка должна быть расшарена в Windows.
- Папки не должны быть **вложены друг в друга**: `C:\Data` и `C:\Data\backup` —
  это копирование папки внутрь самой себя, синхронизация с такой парой не
  начинается.

## Как работает логика синхронизации

Синхронизация — **зеркальная**: приёмник приводится к точной копии источника.
Какая сторона источник, а какая приёмник — задаёт переключатель направления.

### 1. Сравнение файлов

Для каждой выбранной ветки приложение рекурсивно собирает список файлов на обеих
сторонах и сопоставляет их **по относительному пути** внутри ветки. Для каждого
файла решение принимается так:

| Ситуация | Действие |
|---|---|
| Файл есть в источнике, нет в приёмнике | **копировать** |
| Файл есть в обоих, но отличается | **перезаписать** |
| Файл есть в приёмнике, нет в источнике | **удалить** |
| Файл одинаковый | ничего |

«Отличается» = разный размер **или** разное время изменения (mtime). Время
сравнивается с допуском **2 секунды**: разные файловые системы (NTFS, сеть)
округляют mtime по-разному, и без допуска одинаковые файлы считались бы разными.
Содержимое побайтово не сверяется — только размер и дата (это быстро и в 99%
случаев достаточно).

**Регистр в путях не значим.** NTFS и сетевые шары не различают `Docs` и `docs`,
поэтому стороны сопоставляются так же. Иначе один и тот же файл выглядел бы
двумя разными: копия легла бы поверх собственного файла приёмника, а исходное
написание было бы удалено. Если разошлось написание **имени файла**, он всё
равно перезаписывается — так на приёмнике остаётся имя ровно в том виде, в каком
его пишет источник.

А вот разное написание **папки-предка** (`архив/a0/файл.txt` против
`архив/A0/файл.txt`) поводом к работе не считается, и это принципиально. Папку
никто не переименовывает: план структуры считает оба написания одной и той же
папкой и ничего не создаёт, а скопированный файл встаёт в уже существующую —
для Windows это тот же путь. Разница написания остаётся навсегда. Считай мы её
отличием, файл попадал бы в перезапись на **каждом** запуске: предпросмотр
обещает работу, работа выполняется, следующий предпросмотр обещает ровно ту же —
и так до бесконечности, а по сети это ещё и перекачка целых веток на каждом
прогоне. Сравнивается поэтому только имя самого файла.

Правило сквозное — на регистр не смотрит ни одно сравнение путей между сторонами,
и это важнее, чем кажется:

- **Структура папок.** `Док` на приёмнике рядом с `док` на источнике больше не
  считается лишней папкой: иначе `rmdir` сносил бы её сразу после `mkdir`.
- **Конфликты «папка против файла»** ищутся по тому же ключу.
- **Индекс фонового обхода.** Имя ветки интерфейс берёт со стороны, попавшей
  в список первой. Если вторая пишет его иначе, точное сравнение не находило
  в индексе ни одного пути и читало сторону пустой — а пустой источник по логике
  зеркала означает «стереть ветку на приёмнике целиком». Самый опасный случай:
  ловился он только при включённом подсчёте размеров, потому что живой скан
  того же выбора отрабатывал верно.
- **Дерево в интерфейсе.** `Docs` и `docs` — одна строка, а не две, каждая
  с пометкой «нет на другой стороне».
- **Отметки выбора.** Когда сторона возвращается после обрыва, написание имени
  может смениться на её собственное. Ключ отметки подгоняется под новый список,
  иначе выбор разом и стирался, и переставал совпадать со строкой в дереве.

### 1а. Перемещения: метаданных мало

Пара «пропал на приёмнике / появился на источнике» с одинаковым именем, размером
и датой — это пока только **кандидат**. Перед тем как развернуть копирование
в переименование на приёмнике, содержимое сверяется.

Без сверки совпадения хватало, чтобы молча испортить данные. Два разных
`config.json` по 512 байт получают одинаковую дату пачкой — при распаковке архива,
`git checkout`, `robocopy`. Приёмник переименовывал свой старый файл в новый путь
и получал чужое содержимое. Заметить это изнутри приложения было нельзя: следующий
запуск видел совпадающие имя, размер и дату и отчитывался «без изменений».

Сверяются **края файла** — по 64 КБ с начала и с конца, а файл до 128 КБ читается
целиком. Смысл перемещения в том, что оно стоит одного `rename`: читать целиком
дерево на сотню гигабайт значило бы отдать всю выгоду. Мелкие файлы — как раз те,
что чаще всего совпадают по имени и размеру, — сверяются полностью.

Оговорка: два файла крупнее 128 КБ, совпавшие по имени, размеру, дате и обоим
краям, но разошедшиеся в середине, сверку пройдут. Такое совпадение надо строить
намеренно.

### 2. Конфликты «папка против файла»

Под одним именем на разных сторонах может лежать разное: на источнике `Отчёты` —
папка, а на приёмнике файл, или наоборот. Просто скопировать поверх тут нельзя:
`readdir` по файлу обрывает скан с `ENOTDIR`, `mkdir` упирается в файл, а
копирование файла поверх папки падает с `EPERM`.

Поэтому такой узел разбирается отдельной фазой, самой первой: приёмник целиком
расчищает это место, и только потом идут обычные копирование и создание папок.
Всё, что лежало внутри убранного узла, из плана вычёркивается: к моменту
пофайловой обработки его там уже нет. В сводке предпросмотра конфликты
считаются удалениями, и это честно — с приёмника узел действительно убирается.

Ловятся конфликты на самой ветке, в любой её глубине **и в её предках**. Последнее
долго оставалось дырой: выбрали `a/b`, а на приёмнике `a` — файл. Внутрь файла
не проходит ничего, `mkdir` отвечает `EEXIST`, копирование — `ENOTDIR`, и так на
каждом запуске. Ветка не синхронизировалась никогда, а отчёт показывал горсть
ошибок с путями, которых на приёмнике вообще нет.

Один и тот же конфликтный узел от разных веток убирается один раз: у двух выбранных
веток бывает общий предок. Повторный заход нашёл бы на его месте пусто и записал
бы в отчёт файл, удалённый безвозвратно, — хотя тот цел и лежит в служебной папке.

Убранный узел уезжает
тем же путём, что остальные оригиналы, в служебную папку, поэтому «Остановить»
возвращает его на место. Возвращается он последним из всего: на его месте успела
встать папка из более поздних фаз, и место освобождается только в самом конце
отката.

### 3. Удаление — всегда безвозвратное, Корзина не участвует

Лишние файлы на приёмнике удаляются напрямую. Корзины в приложении нет ни на
локальной стороне, ни на сетевой, и предпросмотр предупреждает об этом всегда,
пока есть что удалять.

Так было не сразу, и история тут важнее правила. Сначала удаление шло в **Корзину
Windows** (`shell.trashItem`), но на сетевых путях она отвечает «Failed to perform
delete operation» и обрывала синхронизацию целиком. Тогда сетевую сторону перевели
на прямое удаление, а стороны различали **по виду пути**: сетевым считался только
путь вида «две обратные косые, имя компьютера, имя папки». Дыра осталась ровно там,
где её не видно, — **та же самая шара, подключённая буквой диска** (`Z:`), под
правило не попадала. Предпросмотр обещал Корзину, удаление шло мимо неё, и узнать
об этом можно было только из итога, постфактум.

Обещание, которое зависит от того, каким из двух способов записан один и тот же
сетевой каталог, хуже отсутствия обещания: человек решает судьбу файлов по подписи
в окне. Поэтому Корзину убрали совсем — одно поведение везде, одно предупреждение
везде, и обещать больше нечего.

Отдельной цифры «удалено безвозвратно» в итоге тоже не осталось. Она считалась
весом служебной папки, которая уезжает одним действием, — а в этом весе лежат
не только удалённые файлы, но и **заменённые оригиналы**: после десяти перезаписей
и одного удаления отчёт показывал «безвозвратно: 11». Пока Корзина существовала,
цифра хоть что-то различала («ушло мимо неё»); теперь мимо уходит всё, и сказать
она может только неправду. Сколько удалено, говорит обычная сводка запуска,
а предупреждение стоит там, где оно нужно, — **до** нажатия кнопки.

Сам вес вызова внутри `applyPlan` никуда не делся и по-прежнему закреплён законом
в фуззерах: главный процесс им сейчас не пользуется, но это часть договора —
вызывающий обязан иметь возможность узнать, сколько файлов уносит одно действие.
Вес считается по файлам, а не по узлам: почти везде это одно и то же, и только
конфликт типа уезжает целой веткой — папка на приёмнике, на месте которой
у источника файл.

### 4. Выбор веток и исключения

- Отметили папку → синхронизируется вся её ветка (рекурсивно).
- Внутри отмеченной ветки можно снять галочку с подпапки → она **исключается**:
  не копируется из источника и не удаляется на приёмнике, остаётся как есть.
  У родителя с исключённой подпапкой галочка становится «частичной» (чёрточка).
- Выбор описывается набором **включений** (корни веток) и **исключений** (дырки
  внутри них). При сканировании исключённые ветки просто пропускаются на обеих
  сторонах, поэтому исключённые файлы гарантированно не трогаются.
- Исключения раскладываются по веткам **один раз на запуск**, подъёмом по пути.
  Раньше сканер просил у главного процесса список исключений на каждую ветку
  и на каждую сторону, а тот перебирал его целиком: 5000 веток на 30 тысяч
  исключений — 88 секунд тишины ровно между сканом и появлением предпросмотра.
  Оба числа растут из одного места — отметок в дереве, — поэтому и встречаются
  вместе. Путь достаётся всем своим веткам-предкам, а не ближайшей: вложенная
  ветка выбирается вместе с родителем, и запрет внутри неё виден обеим.
- **Клик по «частичной» галочке включает ветку целиком.** Чёрточка рисуется
  одинаково и когда ветка отмечена со снятой подпапкой, и когда отмечена только
  подпапка, а сам родитель нет. Раньше решение принималось по внутреннему
  состоянию, которого на экране не видно: в первом случае клик разом стирал весь
  выбор, во втором — включал ветку. Две одинаковые с виду чёрточки вели себя
  противоположно.
- **Самая точная отметка главнее.** Внутри исключённой подпапки можно вернуть
  галочку её вложенной части: отмечено `docs`, снято `docs/a`, снова отмечено
  `docs/a/b` — синхронизируется `docs` без `docs/a`, но вместе с `docs/a/b`.
  Запрет действует только до ближайшей отметки внутри себя.
- Отметки живут в интерфейсе и не пропадают, если сторона на секунду отвалилась:
  недоступная папка читается пустым списком, и по такому списку выбор не чистится.
- Ключ отметки — путь **без учёта регистра**, как и всюду в главном процессе.
  Имя узла в дереве берётся с той стороны, что попала в список первой, и стоит
  второй написать его иначе, как точный ключ переставал совпадать: галочка
  пропадала сама собой, а вместе с ней и папка из синхронизации. Настоящее
  написание при этом сохраняется — его и получает главный процесс.
- Тем же ключом опознаются **сами узлы дерева и раскрытые ветки**. Написание имени
  меняется не в теории: список верхнего уровня обновляется каждые шесть секунд, и
  пока локальная сторона недоступна, имя приходит с сетевой — `док`, а когда она
  возвращается, становится `Док`. По точному ключу это выглядело как другая папка:
  узел выбрасывался вместе с загруженными детьми, раскрытая ветка схлопывалась
  сама собой, и так каждый раз, когда связь моргала. Теперь узел опознаётся без
  учёта регистра, а написание просто подтягивается за листингом.

### 5. Предпросмотр перед выполнением

Перед изменениями показывается окно: сколько файлов будет скопировано,
перезаписано и удалено — по каждой выбранной ветке. Никакие файлы
не меняются, пока не нажата кнопка «Выполнить». Само выполнение идёт **пачкой**
(до 16 файлов одновременно) — по сети это заметно быстрее, чем по одному.

Строка по ветке считает и её собственных родителей: для `год/квартал/неделя` план
создаёт ещё `год` и `год/квартал`, а внутрь ветки они не вложены. Раньше в шапке
они были, а в строке нет — и сумма по строкам не сходилась с итогом. Путь при
этом засчитывается самой длинной подходящей ветке, иначе работа вложенной ветки
утекала бы в родителя, а сама она показывала бы «без изменений».

### 6. Ленивое дерево — быстро даже на больших папках

Дерево грузится лениво: при открытии читаются только имена папок верхнего уровня,
при разворачивании — только прямые подпапки этого узла (один `readdir`).

Файлы читаются **параллельно** (до 32 одновременных запросов) — по сети (SMB), где
всё упирается в задержку каждого запроса, это ускоряет обход в разы.

Создание папок при копировании тоже идёт пачкой: результат `mkdir` запоминается
на всю синхронизацию, поэтому пачка файлов в одну папку обходится одним вызовом,
а не вызовом на файл. Запоминается именно обещание, а не отметка о готовности —
отметка ставилась после ожидания, и вся пачка параллельных копий успевала
проскочить проверку до того, как первый допишет ответ.

Фоновый обход при запуске проходит по всем файлам, считает размеры и **запоминает
по каждому файлу размер и дату**. Когда обход завершён (в статус-баре «Готово»),
предпросмотр и синхронизация **переиспользуют эти данные** и не читают сеть заново —
план строится мгновенно. Если обход ещё идёт, выбранные ветки сканируются вживую.
Данные сбрасываются после синхронизации, при «Обновить» и при смене доступности
стороны. Сверх того у кеша сканов есть свой срок — те же **15 минут**, что и у
индекса: связка «предпросмотр → выполнить» укладывается в минуты, а всё, что живёт
дольше, описывает уже не тот диск. Просроченные записи из кеша сканов
выбрасываются: ключ — это путь ветки плюс исключения, разных за сессию набирается
сколько угодно, а запись держит по строке на каждый файл ветки.

Погашённый обход не дописывает свой черновик на диск: токен гасит не только сам
подсчёт, но и сохранение. Иначе оборванный обход сохранялся уже после того, как
пришедший ему на смену успевал записать полный, и следующий запуск показывал
половину дерева как готовые размеры.

Размеры индексируются по пути **без учёта регистра**. Стороны могут писать одну
и ту же папку по-разному, а строка в дереве одна: при точном ключе размеры
расходились по двум записям, и та сторона, чьё написание в дерево не попало,
не показывалась вовсе — рядом с именем висела пустота.

Готовому обходу верят не всегда. Индекс годится вместо живого скана, только если
каждая сторона была на месте и до, и после обхода: пропавшая посреди работы сеть
даёт частичную картину, а по ней приёмник выглядит лишним целиком. И оба пути,
живой скан и индекс, обязаны давать один и тот же план — это проверяют тесты,
которые строят план обоими способами и сверяют результат.

Пока открыт предпросмотр, фоновая проверка связи не перезапускает обход: сеть
одна, и подсчёт размеров вставал бы вторым потоком поперёк копирования.

В список рисуется не больше **500 строк на уровень** (и на верхнем тоже), остальное
сворачивается в «…ещё N». Дело не в чтении, а в отрисовке: во время обхода дерево
перерисовывается раз в 400 мс, и на папке с десятками тысяч подпапок окно вставало
намертво. На выбор предел не влияет: отметки живут отдельно от строк, поэтому
«Выбрать все» захватывает и то, что не показано.

Именно это и делает **число отметок независимым пределом**, который перемножается
со всеми остальными. «Выбрать все» на папке с 30 тысячами узлов верхнего уровня
отмечает все 30 тысяч, и дальше каждый шаг платил произведением:

- **чёрточка «внутри есть отметки»** перебирала все отметки — на каждую из 500
  нарисованных строк. Треть секунды на перерисовку при перерисовке раз в 400 мс:
  окно почти стояло. Теперь цепочки родителей размечаются один раз на правку
  выбора, а строка спрашивает готовый ответ. Правки отметок идут через три
  функции, и каждая этот ответ сбрасывает — иначе дерево рисовало бы чёрточки
  по устаревшему снимку выбора;
- **счётчики по веткам** в предпросмотре искали ветку перебором всех веток на
  каждый путь плана. 5000 отмеченных веток на 100 тысяч файлов — пять с половиной
  секунд замершего главного процесса ровно между сканом и появлением окна. Теперь
  ветка ищется подъёмом по пути до первого совпадения в карте, а цепочки родителей
  размечаются заранее одним проходом. Результат тот же, цена линейна;
- **список веток в предпросмотре** строил строку на каждую отмеченную ветку одним
  `innerHTML` — десятки тысяч строк разметки, почти все со словами «без изменений»,
  то есть ни о чём. Сверх 500 веток остаются только те, где есть работа, а
  остальные сворачиваются в одну строку числом. Пока веток меньше — показываются
  все, включая пустые: список заодно подтверждает, что отмечено именно то, что
  отмечал человек.

### 7. Устойчивость к ошибкам

Ошибка отдельного файла не обрывает всю синхронизацию — проблемные файлы
копятся и показываются в итоге, а остальные обрабатываются нормально:

- **Перенос даты** (`utimes`) на сетевых шарах часто запрещён — это не критично,
  файл всё равно копируется (при следующей синхронизации может считаться
  изменённым по дате).
- **Read-only** файлы при копировании/удалении: снимается атрибут и повтор.
- **Исчезнувший источник** (файл удалили уже после сканирования) идёт в список
  ошибок, а не пропускается молча. Если оригинал на приёмнике к этому моменту уже
  отложен в служебную папку, он возвращается на место: заменять его нечем, и без
  возврата файл пропал бы сразу с обеих сторон.
- **Обрыв посреди работы** не оставляет в неведении: окно отдельно сообщает,
  сорвался ли запуск, не успев ничего тронуть, или ошибка случилась уже по ходу
  записи и часть работы сделана.
- Предпросмотр можно **отменить**, при обрыве связи он показывает ошибку, а не виснет.

**Файл, исчезнувший под руками, не обрывает обход.** Между `readdir`, который
показал файл, и `stat`, который читает его размер, проходит время, а папка живая:
временные файлы, кеш браузера, каталог сборки появляются и пропадают постоянно.
Раньше любая осечка `stat` рушила весь скан целиком — предпросмотр отвечал
«не удалось прочитать папки», синхронизация не начиналась, а фоновый подсчёт
размеров падал на всём дереве, и всё это из-за одного временного файла. Теперь
исход разбирается по коду ошибки:

- `ENOENT` — файла действительно нет, и отсутствие его в списке и есть правда;
- `EPERM`/`EACCES` — файл есть, но размера мы не знаем. Молча выбросить нельзя:
  пустое место на источнике означает «на приёмнике лишнее», и копия уехала бы
  и была бы удалена. Такой файл уходит наверх тем же списком, что и закрытые папки,
  и выводится из сравнения на обеих сторонах;
- остальное (кончились дескрипторы, оборвалась сеть) по-прежнему прерывает обход:
  строить план по неполным данным опаснее, чем не строить его вовсе.

Ошибка файла обрабатывается вторым аргументом `then`, а не отдельным `catch`:
`catch` поймал бы и `aborted`, которым отменяется предпросмотр, и отмена утонула
бы вместе с ошибками файлов.

Отдельно — **защита от «пустого источника»**. Отсутствующую папку сканеры отдают
пустым списком, а пустой источник по логике зеркала означает «на приёмнике всё
лишнее». Поэтому обе стороны проверяются перед тем, как строить план, и синхронизация
просто не начинается, если одна из них недоступна. Ту же осторожность соблюдают
листинг дерева (по нечитаемой стороне список не подменяется) и фоновый обход
(частичный индекс не идёт в план).

**Нечитаемая сторона не выдаётся за опустевшую.** Листинг детей глушит ошибку
намеренно: отвалившаяся сеть не должна рушить весь список, вторая сторона
по-прежнему годится к показу. Но пустой список тогда означает сразу две разные
вещи — «папка пуста» и «прочитать не вышло», — и различал их отдельный `stat`.
`stat` тут не годится: это другой системный вызов, и по закрытой правами папке
он проходит, тогда как `readdir` нет. Сторона объявлялась доступной с пустым
списком, интерфейс верил ответу и стирал отметки папок, которые жили только на
ней. Список верхнего уровня обновляется каждые шесть секунд, так что одна осечка
чтения уносила весь выбор пользователя. Теперь достоверность списка сообщает сам
листинг, тем же ответом, что и содержимое.

**Папки, закрытые правами, обходятся стороной — но на обеих сторонах сразу.**
Такие папки встречаются чаще, чем кажется: `System Volume Information` и
`$RECYCLE.BIN` в корне диска, чужие каталоги на общей шаре. Раньше первая же
такая папка обрывала работу целиком: `readdir` отвечал `EPERM`, предпросмотр
показывал ошибку вместо плана, синхронизация не начиналась вовсе, а фоновый
подсчёт размеров падал на всём дереве. Выбрать корень диска было попросту нельзя.

Подменить содержимое закрытой папки пустым списком — не выход, а способ потерять
данные: пустой источник означает «на приёмнике всё лишнее», и одна ошибка прав
стёрла бы с приёмника живую ветку целиком. Поэтому закрытый узел выбывает из
сравнения **на обеих сторонах разом**: его содержимое не копируется, не
удаляется и не перезаписывается ни там, ни там. Сам узел тоже выбывает — он
существует, просто внутрь не пускают, — поэтому его не создают на пустом месте
и не сносят с приёмника. Список таких узлов показывается в предпросмотре до
запуска и в итоге после него, а обход размеров вместо «Готово» пишет, сколько
папок и файлов осталось без доступа.

Закрытым бывает не только каталог, но и отдельный файл: тогда не читается даже
его размер, и сравнивать его не с чем точно так же. Раньше выбывание работало
только по вложенным путям, поэтому названный целиком файл не отсекал сам себя —
и его копия на приёмнике выглядела лишней. Теперь путь из этого списка
сопоставляется и целиком, и как префикс.

Из-за этого же список перестал быть коротким. Пока в него попадали одни папки,
записей было единицы: внутрь закрытой папки не спускаются, и вся ветка стоит одной
строки. Отдельные файлы всё изменили — шара, где папку листать дают, а `stat`
по файлам нет, отдаёт запись на каждый файл. Проверка «лежит ли путь внутри
закрытого узла» перебирала при этом весь список на каждый путь ветки, и два
законных предела перемножались: тысяча закрытых записей на ветку в 50 тысяч файлов
давала **десять секунд** замершего главного процесса ровно между сканом и
появлением предпросмотра — и это на каждую выбранную ветку отдельно, а двадцать
тысяч закрытых записей превращались уже в три с половиной минуты. Теперь проверка
идёт подъёмом по пути до первого совпадения в наборе: цена — глубина пути, а она
измеряется единицами. Те же входные данные считаются за 0,1 секунды.

Тот же вопрос — «лежит ли путь внутри одного из названных узлов» — задают ещё
в трёх местах, и подъёмом по пути они считают давно. А в четвёртом, при разборе
индекса фонового обхода, остался перебор всего списка исключений на каждый путь.
Исключения — это снятые галочки, и растут они вместе с деревом: 800 снятых веток
на 200 тысяч файлов давали **16 секунд** замершего главного процесса. Заметить
это было тем труднее, что платил за него только тот, у кого включён подсчёт
размеров: живой скан до исключённой ветки просто не доходит, а индекс сравнивает
полные пути. Расхождение соседей — «одно и то же делается в трёх местах, а
в четвёртом иначе» — так и осталось самым дешёвым способом такое находить.

Считаются закрытыми только `EPERM` и `EACCES`. Прочие сбои чтения (кончились
дескрипторы, оборвалась сеть) по-прежнему прерывают обход с ошибкой: принять их
за «закрытую папку» значило бы строить план по неполным данным.

Живой скан и индекс фонового обхода ведут себя тут одинаково — иначе включённый
подсчёт размеров менял бы результат синхронизации, а такую разницу пользователю
ни увидеть, ни объяснить.

**Вложенные корни отклоняются.** Пара вроде `C:\Data` и `C:\Data\backup` — это
копирование папки внутрь самой себя: приёмник растёт по ходу работы, и уже
скопированное на следующем проходе снова выглядит новым. Такая пара не проходит
проверку, и синхронизация не начинается. Регистр и завершающий слэш на проверку
не влияют, а вот соседние `data` и `data2` пересечением не считаются.

**Застрявший оригинал не выбрасывается заодно с мусором.** В конце запуска
служебная папка стирается целиком, одним действием: это на порядок
быстрее, чем по файлу. Но если внутри остался оригинал, который не удалось ни
заменить, ни вернуть на место (путь занят, файл держат открытым), другой копии
у него нет. Тогда папка целиком не трогается: стирается поимённо только
то, что записано в журнале, а застрявшее дожидается следующего запуска. Тот
разберёт служебную папку на старте, когда помеха может уже исчезнуть. Осечка на
одном оригинале при этом не отменяет уборку остальных — иначе уже заменённые
файлы вернулись бы на приёмник следующим запуском, как будто их и не удаляли.

**Служебную папку разбирает и предпросмотр, а не только запуск.** Раньше это
делал один запуск, и после вылета два взгляда на одно дерево расходились:
предпросмотр видел на месте отложенного файла дыру и обещал скопировать его
заново, а запуск сначала возвращал оригинал на место и работы уже не находил.
Человек соглашался на «скопировать 1» и получал «0/0 Готово». Разбор вынесен
в общее место и зовётся из обоих — как и всё, что решает, что именно попадёт
в план.

**Разбор служебной папки идёт узлами, а не файлами.** Если на месте узла ничего
нет, один `rename` возвращает всё поддерево разом — по сети это одна операция
вместо тысячи. Место занято папкой — содержимое сливается по одному, вглубь.
Пустые папки при этом сохраняются: раньше возврат шёл по списку файлов, а
«пусто ли внутри» считалось тем же списком, и отложенная ветка без единого файла
не возвращалась вовсе — служебная папка проходила по такому счёту как пустая и
стиралась вместе с ней. Теперь содержимое считается обходом каталогов: файл,
ссылка или непустая ветка означают, что узел вернуть не удалось.

Второй экземпляр приложения не запускается: две копии делят служебную папку
`.sgundo` на приёмнике, и разбор брошенных оригиналов одним запуском выдернул бы
их из-под другого. Вместо нового окна поднимается уже открытое.

По той же причине и **вторая синхронизация разом не начинается**: пока идёт одна,
запрос на другую отклоняется с ошибкой. Интерфейс на время работы и так блокирует
кнопку, но полагаться на интерфейс тут нельзя — последствия доходят до файлов.

### 8. История синхронизаций

Каждый непустой запуск записывается в `history.json` (в `userData`): время,
направление, сводка (сколько скопировано / перезаписано / удалено), число
безвозвратных удалений и ошибок, а также список файлов. Хранятся **последние
200 запусков**; в одной записи — до 5000 файлов (удаления в приоритете, остальное
помечается как «…ещё N»). Запись атомарная. Кнопка «История» показывает журнал,
запись раскрывается в список файлов; есть очистка.

Поимённые списки хранятся только у **последних 20 запусков**; у остальных
остаётся строка с итогами и числом файлов. Иначе два предела перемножались:
200 запусков по 5000 файлов — это 87 МБ в `history.json`, который целиком
перечитывался и переписывался после каждой синхронизации, целиком уезжал
в интерфейс и целиком превращался в миллион строк разметки. Окно истории на
таком журнале вставало намертво. По той же причине список файлов запуска
строится только в момент, когда запуск раскрывают, а не для всех сразу.

Битые записи внутри журнала отсеиваются **на чтении**, а не у каждого читателя
по отдельности. Проверка того, что файл вообще массив, была, а вот записи внутри
никто не проверял: одного `null` в файле хватало, чтобы разметка окна истории
оборвалась на полуслове и окно навсегда осталось на «Загрузка…». Достоверность
данных выясняется там же, где их берут, — иначе каждый следующий читатель
начинает с нуля и кто-нибудь обязательно забудет.

**Все три файла состояния пишутся атомарно** — во временный файл и переименованием
поверх: история, кеш размеров и настройки. У настроек этого не было: обычный
`writeFile` сначала обрезает файл, и вылет или обрыв питания между обрезанием
и записью оставлял пустой `settings.json`. Следующий запуск молча забывал обе
выбранные папки — а это единственное, что пользователь настраивает руками.

Осиротевшие временные файлы (`.tmp`) от прерванных атомарных записей кешей,
истории и настроек удаляются автоматически при старте. Тогда же прореживаются
кеши размеров: файл `sizecache-*.json` заводится на каждую пару путей и живёт
вечно, а на дереве в сотни тысяч узлов весит десятки мегабайт — остаются шесть
последних.

## Архитектура

Electron, два процесса, общение через IPC (безопасный мост `contextBridge`):

- **Main (Node.js)** — вся работа с файлами: листинг, параллельное сканирование,
  фоновый обход размеров, сравнение, копирование, удаление, проверка доступности,
  кеши и хранение настроек.
- **Renderer** — интерфейс liquid glass. Файловой системы напрямую не касается,
  только шлёт запросы в main и рисует дерево/статусы/прогресс.

### Модули

- `src/sync.js` — **чистая логика планирования**: на вход два списка файлов, на
  выход план (копировать / перезаписать / удалить / без изменений), поиск
  перемещений (`detectMoves`), разница структуры папок (`planDirs`), сводка для
  предпросмотра (`summarize`). Без файловых операций — легко тестируется.
- `src/plan.js` — **сборка плана на весь запуск**: план по одной ветке
  (`planForBranch`, включая конфликты «папка против файла» на ветке, внутри неё
  и в её предках), слияние всех выбранных веток в один план (`buildRunPlan`) —
  только так виден перенос файла между двумя ветками, — сверка кандидатов
  в перемещения по содержимому (`confirmMoves`), чтение ветки из готового индекса
  обхода (`scanFromIndex`), раскладка всего индекса по веткам запуска за один
  проход (`groupIndexByBranch` — тем и живёт запуск, а `scanFromIndex` остался
  мерилом её правильности) и счётчики по каждой ветке для предпросмотра
  (`countByFolder`). Файловую систему трогает только через `stat`, сверку
  содержимого и переданный сканер, поэтому тестируется на временных папках.
- `src/fsops.js` — файловые операции: параллельный рекурсивный скан (с исключениями
  и списком того, что закрыто правами — папок и отдельных файлов), ленивый листинг
  детей с датой и признаком «папка прочитана» (`listChildren`), фоновый обход
  дерева (`crawlTree`), сверка двух файлов по краям (`sameContent`), выполнение
  плана с устойчивостью к ошибкам отдельных файлов, журнал и откат (`applyPlan`,
  `restoreStage`), служебная папка `.sgundo`.
- `src/paths.js` — проверка вложенности корней друг в друга (`rootsOverlap`) и ключ
  сравнения путей без учёта регистра (`ciKey`), которым пользуются все остальные
  модули. Свёртки вложенных выбранных путей здесь намеренно нет: вложенная ветка
  рядом с родителем — законный выбор (см. «Выбор веток и исключения»), и отбрось
  её как «покрытую», она молча выпала бы из синхронизации.
- `main.js` — Electron main: IPC (листинг, предпросмотр с прогрессом/отменой,
  синхронизация, фоновый обход, проверка доступности `probe`, история), кеш сканов
  в памяти и кеш размеров на диске (`sizecache-*.json`), история (`history.json`,
  с прореживанием поимённых списков), настройки (`settings.json`), очистка `.tmp`
  и лишних кешей размеров при старте — всё в `userData`.
- `preload.js` — узкий IPC-мост.
- `renderer/` — интерфейс: `index.html`, `styles.css`, `renderer.js` (дерево,
  трёхпозиционный выбор, сортировка, статус-бар, индикаторы связи).
- `docs/superpowers/specs/` — исходный дизайн-документ (снимок на старте проекта).
- `test/` — юнит- и интеграционные тесты (`node --test`); в `test/helpers/`
  заглушки Электрона и DOM, которыми поднимаются `main.js` и `renderer.js`.

## Тесты

```powershell
npm test
```

Тринадцать файлов в `test/`, 190 тестов, всё на `node --test`, без внешних
зависимостей. Логика вынесена в `src/` и проверяется напрямую, а `main.js`
и `renderer.js` поднимаются с заглушками: Электрон и DOM подменяются
в `test/helpers/`. Настоящий Электрон для тестов не нужен.

- `sync.test.js` — сравнение файлов, поиск перемещений, разница структуры папок,
  сводка, нечувствительность к регистру. Чистые функции, на списках в памяти.
- `paths.test.js` — проверка вложенности корней друг в друга.
- `plan.test.js` — сборка плана на временных папках: слияние веток, перенос между
  двумя выбранными ветками, вложенные ветки и их родители, исключения, конфликты
  «папка против файла» (в том числе в предке ветки и общий предок двух веток),
  отсев ложных перемещений по содержимому, счётчики предпросмотра, ветка в чужом
  регистре, закрытый правами файл на источнике (копия на приёмнике обязана
  уцелеть). Отдельно сверяется, что план по индексу фонового обхода совпадает
  с планом по живому скану — источники разные, а результат обязан быть один, —
  и что ни счётчики по веткам, ни выбывание закрытых правами узлов, ни сам разбор
  индекса не платят произведением двух пределов. Отдельным тестом закреплено, что внутренняя папка,
  написанная на приёмнике в другом регистре, не заводит вечную перезапись.
- `fsops.test.js` — реальный цикл копирование/перезапись/удаление, изоляция
  вложенной синхронизации, откат по журналу, разбор служебной папки после
  оборванного запуска (включая пустые папки и ветки без единого файла),
  устойчивость `applyPlan` к ошибке отдельного файла и к отказу удаления,
  а также то, что `mkdir` не уходит на каждый скопированный файл.
- `stress.test.js` — случайные изменения дерева с проверкой, что после
  синхронизации стороны совпадают, а повтор не находит работы; остановка в
  произвольной точке с возвратом приёмника ровно в исходное состояние; ветка на
  200k файлов.
- `main.test.js` — IPC-обработчики на настоящих временных папках, тем же путём,
  каким ходит интерфейс: листинг и слияние сторон, предпросмотр, синхронизация
  в обе стороны, исключения и вложенные ветки, файл на месте папки-предка, отказ
  при недоступной стороне и при вложенных корнях, замок на одновременный запуск,
  остановка с откатом, разбор брошенных оригиналов, история, битые файлы состояния.
  Отдельно — закрытие окна посреди обхода: заглушка теперь отдаёт наружу и события
  самого приложения, поэтому сохранение прогресса при выходе проверяется тем же
  путём, каким оно происходит.
- `renderer.test.js` — модель выбора в дереве: трёхпозиционные отметки,
  наследование включения и исключения, нечувствительность к регистру, поведение
  клика по «частичному» узлу, сохранение отметок при моргнувшей связи,
  форматирование размеров, экранирование, сортировка. Отдельно — смена написания
  имени на лёгком обновлении списка: узел обязан опознаться, раскрытая ветка
  с загруженными детьми — уцелеть, а строка — перерисоваться под новое написание,
  и только под него: лишних перерисовок каждые шесть секунд быть не должно.
  Отдельно же — пределы: чёрточки не платят произведением строк на отметки,
  запомненный ответ про отметки внутри слетает на каждой правке выбора, а список
  веток в предпросмотре сворачивается вместо строки на каждую из тысяч.
- `denied.test.js` — папки, закрытые правами (доступ снимается настоящим `icacls`
  и возвращается после теста): обход их переживает и называет, содержимое
  не удаляется с приёмника и не копируется на него вслепую, живой скан и индекс
  обхода дают один и тот же план, закрытый корень ветки выводит её из работы целиком.
  Отдельно — нечитаемый корень на уровне IPC: сторона обязана числиться
  недоступной, а не доступной с пустым списком.
- `racing.test.js` — папка меняется под руками у обхода. `stat` подменяется так,
  чтобы по одному пути отвечать ошибкой: настоящую гонку «файл исчез между
  `readdir` и `stat`» иначе не воспроизвести, она зависит от того, кто успел
  первым. Проверяется, что `ENOENT` просто убирает файл из списка, `EPERM` уводит
  его в список закрытых, прочие коды по-прежнему обрывают обход, а отмена
  предпросмотра пробивается сквозь новую обработку ошибок. Тут же — что листинг
  детей отличает пустую папку от нечитаемой.
- `history.test.js` — пределы журнала: поимённые списки только у последних
  запусков, срез старых при новой записи, отложенная сборка строк в окне истории,
  а также отсев битых записей внутри массива прямо на чтении.
- `scaling.test.js` — **законы масштаба**: сеть на класс «произведение двух
  пределов», а не замер на один найденный адрес. Растёт одно измерение входа
  (исключения) при неизменном дереве и неизменном числе веток: у здорового кода
  цена не меняется (×1.2), у любого, кто перебирает исключения внутри перебора
  веток, — растёт вчетверо. Меряется настоящий обработчик предпросмотра, обе
  дороги сразу (живой скан и индекс обхода), и тот же прогон отвечает на второй
  вопрос: не спрашивали ли у диска один и тот же путь дважды — повторное чтение
  растёт линейно, осью его не поймать, а на сетевой шаре оно и стоит дороже
  всего. Закон проверен тремя мутациями, и одна из них — чужая: дефект прошлой
  ревизии, возвращённый в код, ловится без единого упоминания его места.
- `invariants.test.js` — **дифференциальные прогоны на случайных деревьях**: не
  «проверить сценарий», а сформулировать закон и попробовать его сломать.
  Тринадцать законов. Первые шесть про ядро: приёмник становится точной копией
  источника; второй прогон не находит работы (в том числе с исключениями);
  остановка в любой точке возвращает приёмник ровно как было; план по индексу
  обхода совпадает с планом по живому скану; при случайно падающих файловых
  операциях ни один файл не исчезает с обеих сторон; предпросмотр не врёт —
  сумма счётчиков по веткам равна итогу в шапке, а повтор пуст, причём приёмник
  тут не отдельное случайное дерево, а искажённая копия источника.

  Остальные шесть добавлены ревизией 17.08.2026 и закрывают весь прежний список
  «чего эти законы не спрашивают»:

  - **цепочка прогонов** в обе стороны с обрывами и вылетами. Направление, точка
    обрыва и вылет выбираются случайно, а законов сразу три: источник не трогают
    никогда, оборванный прогон возвращает приёмник как было, доведённый — сводит
    стороны. Вылет имитируется руками: настоящий `applyPlan` так не заканчивает,
    он либо доводит дело до конца, либо откатывает, и получить служебную папку
    от «умершего» запуска иначе неоткуда;
  - **клики по дереву**. Прочие законы зовут `buildRunPlan` с готовым списком
    веток и исключений, то есть проверяют вторую половину пути. Здесь кликают
    по случайным узлам через `renderer-harness`, а закон сверяет две независимые
    вещи: что показывает строка на экране (`isIncluded`) и что после этого
    действительно происходит с файлом на диске;
  - **дерево, меняющееся посреди работы**. Файлы удаляются, дописываются
    и подменяются папками прямо между фазами `applyPlan`, а закон требует двух
    вещей: работа не срывается исключением, и приёмник меняется ровно там, где
    обещал план. Порча вносится по счётчику действий, а не по таймеру, — иначе
    упавший прогон не повторить. Первый удар всегда прицельный: с источника
    сносится файл, обещанный к перезаписи, и его оригинал на приёмнике к этому
    моменту уже отложен в служебную папку;
  - **вес вызова удаления** сверяется с тем, сколько файлов вызов на самом деле
    уносит. Это обещание, на котором главный процесс считает «удалено
    безвозвратно», и на сетевом приёмнике оно единственное, что человек узнает
    о потере;
  - **история как отчёт**. Сверяется в обе стороны: каждая строка записи
    подтверждается диском, и каждый изменившийся файл назван в записи.
    Односторонняя проверка ловит выдумки, но не умолчания. Направление
    чередуется: «сеть → локально» до этого проходилась только точечно;
  - **имя с диска не становится разметкой**. `escapeHtml` проверялся сам по себе
    и был верен — но верная функция ничего не значит, если её забыли позвать.
    Закон спрашивает результат: имя с угловыми скобками и кавычками прогоняется
    через строку дерева, плашки предпросмотра и окно истории, и ни в одной
    разметке не имеет права оказаться сырым.

  Тринадцатый добавлен следующей ревизией и стережёт правку, а не поведение:
  **раскладка индекса по веткам совпадает с поветочным разбором**. Разбор
  перебирал весь индекс на каждую ветку, раскладка проходит его один раз и ищет
  хозяина пути подъёмом. Способы разные, ответ обязан быть один, и самый тонкий
  вход — вложенные ветки с исключением между ними. Ветки в этом законе не
  случайные, а накликанные через `renderer-harness`: интерфейс других не
  порождает, а закон, проверяющий невозможный вход, ловит только собственные
  выдумки. Плотность генератора закреплена прямо в законе: если вложенных пар
  веток набралось меньше пяти на тридцать прогонов, падает он сам.

  Деревья засеяны числом, поэтому набор один и тот же от запуска к запуску.

  **Чего эти законы не спрашивают.** Зелёный набор значит «ни одного бага,
  до которого дотягиваются эти генераторы», а не «багов нет». Разница между этими
  двумя утверждениями и есть причина, по которой каждая ревизия что-то находит,
  хотя предыдущая объявляла ядро закрытым. Список ниже — не жалоба, а указатель:
  следующая находка почти наверняка лежит на одной из этих осей.

  1. **Пределы.** Произведения двух величин ищутся грепом и арифметикой
     на салфетке; автоматически их не ищет ничто. Ревизия 17.08.2026 нашла этим
     ещё одно — исключения на индекс обхода, — а следующая нашла на том же месте
     произведение покрупнее: сам разбор индекса шёл по разу на ветку. Соседний
     предел починили, а этот, лежавший строкой выше, не заметили. Закона тут и не может быть в прежнем
     смысле: прогон на случайных деревьях меряет правильность, а не цену, а цена
     проявляется только на величинах, которых в прогоне не бывает. Ближайшее
     к закону — точечные замеры с бюджетом времени в `plan.test.js`, и их надо
     заводить на каждое новое место, где один список перебирается внутри другого.

     **Так было до `scaling.test.js`.** Заводить замер «на каждое новое место»
     и означало ловить по одному адресу за ревизию: пять ревизий подряд находили
     этот класс, закрывали найденный адрес замером и получали соседний адрес
     в следующей сессии. Закон масштаба спрашивает форму, а не адрес: растёт одно
     измерение входа, остальные стоят, и произведение вылезает само — где бы оно
     ни пряталось. Точечные замеры остались как быстрая подстраховка на уже
     известных местах, но искать этот класс ими больше не надо.
     Ревизия после неё нашла на этой же оси ещё два, и оба — рядом с уже
     починенным: исключения на ветки в живом скане (88 секунд) и типы веток,
     которые план спрашивал у диска по одной ветке за раз. Второе стоит отметить
     отдельно: произведение там не в памяти, а в сетевых обращениях, и секундомер
     на локальном диске его не видит вовсе. Такие замеры приходится ставить
     на подменённом `stat` — и мерить не время, а два счётчика: сколько обращений
     всего и сколько их держалось в воздухе разом.
  2. **Настоящая одновременность.** Порча дерева вносится между фазами `applyPlan`,
     а не в середине одной файловой операции: узнать, что будет, если файл исчезнет
     ровно между `stat` и `copyFile`, можно только подменой самих вызовов — так
     и сделано в `racing.test.js`, но точечно, на один путь за раз.
  3. **Второй экземпляр приложения и посторонний процесс.** От второй копии себя
     защищает одиночный замок, но чужая программа, пишущая в те же папки, ничем
     не ограничена. Прогоны портят дерево сами, изнутри — настоящего второго
     писателя с его блокировками файлов тут нет.
  4. **Что видно глазами.** Разметка проверяется на экранирование, но не на смысл:
     что в плашке «скопировать» стоит именно число копий, что полоса прогресса
     дошла до конца, что строка дерева подписана той стороной. Это проверяется
     точечными тестами и запуском приложения руками.
  5. **Электрон сам по себе.** Всё поднимается на заглушках: настоящих окон,
     настоящего IPC в прогонах нет. Корзина этот пункт покинула: приложение
     её больше не зовёт вовсе, и «на сетевой шаре Корзины нет» перестало быть
     допущением, на котором что-то держится. Осталось обратное обязательство —
     что Корзину не зовут и на локальной стороне, — и оно закреплено тестом
     через заглушку `shell.trashItem` в `main.test.js`.

  Эти прогоны написаны при полной ревизии и **нашли ноль расхождений** — все дефекты
  той сессии лежали по краям (права на папку, пределы роста истории, опознание
  узлов дерева). Ноль и есть их ценность: пока они зелёные, ядро не деградировало,
  и следующей ревизии не нужно перепроверять его руками. Все проверены мутацией:
  с внесённой обратно ошибкой (точное сравнение путей, вырезанный возврат
  отложенных оригиналов) они падают. Мутация тут не формальность: шестой закон
  с первого захода прошёл и с багом — редкая папка на редкий шанс перевернуть
  написание давали на сорок прогонов пять подходящих случаев, и ни один не сложился
  до конца. Генератор пришлось сделать гуще и злее, и только после этого закон
  начал ловить. Непроверенный мутацией фуззер — это зелёная галочка ни о чём.

  Следующая ревизия это подтвердила: ядро осталось зелёным, а найденное снова
  лежало по краям — гонка `stat` на живой папке, `stat` вместо `readdir` как
  мерило достоверности листинга, и число отметок, перемножающееся со всем
  остальным. Ни один из этих дефектов фуззер по инвариантам породить не может:
  он не роняет системные вызовы в нужный момент и не отмечает 30 тысяч веток.

  А вот следующая ревизия ядро всё-таки пробила — новым законом, которого тут
  не было: **предпросмотр не врёт**. Приёмник в ней строится не отдельным случайным
  деревом, а искажённой копией источника (переименования, смена написания, конфликты
  типов, лишние файлы), и проверяется тройка: сумма счётчиков по веткам равна итогу
  в шапке; обещанный итог равен отработанному; повтор пуст. Третье и упало — папка,
  написанная на приёмнике в другом регистре, давала вечную перезапись. Прежние пять
  законов этого не видели: деревья у них независимые, и совпадение путей с точностью
  до регистра там почти не встречалось. Мораль та же, что и с краями: фуззер находит
  ровно то, о чём его спросили, и новый закон стоит дороже лишней тысячи прогонов
  по старым.

  Ревизия 17.08.2026 написала сразу три новых закона — по одному на первые три
  оси списка, — и все три вышли зелёными с первого раза. Ядро они не пробили,
  зато пробили сам набор: закон про историю не поймал мутацию «не писать удаления
  в журнал». Причина оказалась в генераторе, а не в законе. `perturbedCopy`
  только искажала копию источника и никогда не добавляла на приёмник лишнего,
  поэтому план почти никогда не содержал удалений — и шестой закон, живший
  на том же генераторе, всё это время проверял их вхолостую. Лишние узлы
  на приёмнике добавлены, мутация после этого ловится.

  Второй раз генератор пришлось чинить в законе про клики: вложенная пара
  «исключено, а внутри снова включено» — то, ради чего выбор и трёхпозиционный, —
  выпадала на случайных кликах четыре раза на тридцать прогонов. Теперь к случайным
  кликам добавлен проход по одной цепочке сверху вниз: клик по каждому предку
  подряд даёт чередование гарантированно. Оба раза дело было не в том, что закон
  сформулирован неверно, а в том, что генератор до нужного случая не доходил, —
  и оба раза это выяснила мутация, а не зелёная галочка.

  Та же ревизия дописала оставшиеся три закона и на них наступила на грабли
  ещё дважды, обе — свои собственные. Закон про дерево, меняющееся на ходу,
  не ловил мутацию «не возвращать отложенный оригинал», потому что сам звал
  перед проверкой `restoreStage`: разбор служебной папки возвращал ровно то, что
  прогон потерял. Ровно предупреждение из закона об остановке, повторённое
  дословно. И он же не доходил до нужного случая: замер показал 62 перезаписи
  на 55 прогонов и ни одного «источник исчез до своей очереди» — перезаписи идут
  последней фазой и составляют считаные проценты шагов. Теперь первый удар
  всегда прицельный, а случайные точки к нему добавляются.

  Закон про вес удаления сразу упал, но не на баге: генератор передавал одну
  и ту же ветку дважды, в двух написаниях (`Doc0` с источника и `DOC0`
  с приёмника), потому что собирал список простым объединением двух `readdir`.
  Интерфейс так не умеет — `list-folders` схлопывает написания по `ciKey`,
  а отметки лежат под тем же ключом и вторым написанием стать не могут. Закон,
  проверяющий невозможный вход, ловит только собственные выдумки; список веток
  в прогонах теперь собирается так же, как в приложении.

  Следующая ревизия ядро снова не пробила и снова нашла на первой оси — там же,
  где предыдущая. Починили исключения на индекс, а строкой выше остался разбор
  индекса по разу на ветку: 5000 накликанных веток на 105 тысяч узлов и две
  стороны — 83 секунды замершего главного процесса ровно между сканом
  и появлением предпросмотра. Живой скан столько не стоит, поэтому платил
  за это только тот, у кого включён подсчёт размеров. Мораль: починенный предел
  не закрывает соседний, а греп «цикл внутри перебора» надо перечитывать
  и по уже правленным местам.

  Следующая ревизия сходила туда же в третий раз и снова не зря. Раскладку
  индекса по веткам чинили для стороны с подсчётом размеров, а живой скан рядом
  остался просить у главного процесса список исключений на каждую ветку и на
  каждую из двух сторон: 5000 веток на 30 тысяч исключений — 88 секунд, и платит
  за них ровно тот, кого прошлая правка не касалась, — с выключенным подсчётом
  размеров. Две правки, зеркальные друг другу, разошлись по разным дорогам,
  и вторая дорога простояла непочиненной ровно потому, что первую объявили
  закрытой.

  Вторая находка той же ревизии — того же рода, но не в памяти. План разбирает
  ветки по одной и на каждую спрашивал у диска тип самой ветки и всей цепочки
  её родителей: у пяти тысяч веток вида `год/квартал/N` предок читался заново
  пять тысяч раз, и все обращения шли строго по очереди. На локальном диске это
  доли секунды — поэтому ни один прежний замер этого не видел, — а на сетевой
  шаре с 3 мс на обращение около минуты тишины между сканом и предпросмотром.
  Теперь типы читаются пачкой до разбора и складываются в памятку на запуск.
  Урок для следующей ревизии: предел, выраженный в обращениях к диску, секундомер
  на локальном диске не ловит вообще, и тест на него приходится писать
  на счётчиках подменённого `stat`, а не на времени.

`main.js` и `renderer.js` долго оставались без тестов — Электрон и DOM мешали их
поднять, — и баги копились именно там. Заглушки в `test/helpers/` эту дыру
закрывают: `main-harness.js` подменяет модуль `electron` и отдаёт наружу
зарегистрированные IPC-обработчики, `renderer-harness.js` поднимает `renderer.js`
в отдельном контексте с крошечным DOM. Сам контекст тоже отдаётся наружу: функции
верхнего уровня лежат на нём свойствами, поэтому их можно подменить и проследить,
что вызов действительно был, — иначе «перерисовалось ли дерево» изнутри теста
никак не увидеть.

Основной приём проверки — **сравнение деревьев целиком** до и после, а не
отдельных файлов. Так ловятся и лишние следы (пустая папка, оставшаяся от
отката), и молчаливые пропуски, которых по сводке не видно.

## Вне рамок

- Нет облака/сервера/сетевых протоколов — только пути файловой системы.
- Нет автосинка по расписанию — синхронизация по кнопке.
- Имя `.sgundo` занято служебной папкой. Свою папку с таким именем ни один обход
  не видит, поэтому в синхронизацию она не попадёт.
- Сравнение по размеру и дате, без побайтовой сверки/хешей. Содержимое читается
  только у кандидатов в перемещения, и то краями.

## Кадры для README собираются программой

`tools/make-screenshots.js` запускает настоящее приложение с отдельной
временной папкой `userData`, чтобы не тронуть ни настройки, ни кеши, ни историю,
и подкладывает две выдуманные папки: «Ноутбук» и «Сетевой ПК». Честно:
«сетевая» сторона здесь — вторая локальная папка, настоящей шары у скрипта нет.
Кадр берётся с самой страницы через `webContents.capturePage()`: снимок экрана
тут не годится, в него может попасть чужое окно.

```powershell
npx electron tools/make-screenshots.js
```

полосы был только у деревьев, теперь он у всех прокручиваемых списков.
